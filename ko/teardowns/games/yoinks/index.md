# yoinks — 보여 주는 크기와 받는 파일이 달랐다

> 주소를 붙여넣으면 영상을 파일로 받아 주는 터미널 도구입니다. 코드를 읽고 그 선택 로직을 실제 영상에 돌려 보니, 화면에 적힌 크기와 실제로 받는 파일이 달랐습니다. 도구는 안 들이고, 쓸 만한 세 가지만 제 스크립트로 옮겼습니다.

**yoinks 는 터미널에 영상 주소를 붙여넣으면, 유튜브·X·인스타그램 같은 곳의 영상을 내 컴퓨터에 파일로 받아 주는 도구입니다.** 직접 받는 건 아닙니다. 실제로 받는 일은 yt-dlp 라는 유명한 받기 프로그램이 하고, yoinks 는 그 앞에 **해상도를 고르는 화면**을 씌운 겁니다.

게임을 만들다 보면 다른 게임의 영상을 오래 두고 봐야 할 때가 있습니다. 한 번 보고 끝이 아니라, 프레임을 하나씩 넘기며 연출을 따져 보는 용도입니다. 그래서 「영상을 파일로 받는 깔끔한 방법」을 열어 봤습니다.

## 화면은 예쁜데, 고르는 일은 두 군데에서 따로 합니다
이 도구에서 제일 눈에 띄는 설계는 **받기 전에 선택지를 보여 준다**는 점입니다. 주소를 넣으면 「1080p · 약 85MB」 「720p · 약 40MB」 「소리만 mp3」 같은 줄이 뜹니다. 그런데 열어 보니 이 목록은 두 가지 규칙이 따로 만듭니다.

| | 하는 일 | 누가 정하나 |
|---|---|---|
| **줄에 적히는 크기** | 후보 중 점수 1등을 골라 그 크기를 적는다 | yoinks 의 점수식 |
| **실제로 받는 파일** | 해상도만 지정해서 yt-dlp 에 맡긴다 | yt-dlp 의 기본 고르기 |

점수 1등과 실제로 받는 파일이 **같은 파일이라는 보장이 없습니다.** 이게 이 글의 핵심입니다.

## 같은 영상으로 재 봤더니 크기가 36% 모자랐습니다
유튜브에서 제일 오래된 19초짜리 영상 하나에, yoinks 의 선택 코드를 **그대로** 돌렸습니다. 결과는 이렇습니다.

| 240p 줄 | 값 |
|---|---|
| 화면에 적히는 크기 | **약 302 KB** |
| 실제로 받게 되는 조합 | 영상 AV1 + 소리 Opus, **476 KB** |

302 KB 는 영상 크기가 아니라 **소리 파일 하나의 크기**였습니다. 점수 1등으로 뽑힌 영상 조각은 크기 정보가 비어 있었고, 코드는 비어 있으면 0으로 치고 소리 크기만 더합니다. 그래서 영상 몫이 조용히 빠졌습니다.

더 있습니다. 144p 줄도, 「소리만」 줄도 똑같이 「약 302 KB」라고 떴습니다. 세 줄이 한 숫자를 나눠 쓴 겁니다.

그리고 점수식은 H.264 를 가산점으로 좋아하는데, 실제로는 AV1 이 받아졌습니다. 이 도구의 이슈 목록에는 「받은 HD 영상이 퀵타임에서 안 열린다」는 글이 열려 있는데, 이 어긋남과 맞아떨어지는 모양입니다(제가 재생을 확인한 건 아닙니다).

## 그래서 도구는 안 들이고, 쓸 만한 것 셋만 가져왔습니다
yoinks 자체는 **저한테 쓸모가 없습니다.** 사람이 키보드로 고르는 화면이라 AI 가 못 쓰고, 「묻지 않고 한 번에 받기」 옵션은 아직 로드맵에만 있습니다. 대신 설계에서 셋을 빼 와서 제 쪽 스크립트 한 장(`ref_video.py`)으로 새로 썼습니다.

| 가져온 것 | 어떻게 바꿨나 |
|---|---|
| **영상 정보를 한 번만 읽고 재사용** | 그대로. 두 번째 읽기를 건너뛰어 시작이 빠르다 |
| **해상도 선택 사다리** | 코덱을 H.264 우선으로 바꿨다. 없으면 다른 코덱으로 내려간다 |
| **중단하면 반쪽 파일 치우기** | 임시 폴더에서만 받고, 실패하면 폴더째 지운다 |

그리고 이 글에서 배운 것을 고쳐 넣었습니다. **적어 주는 크기를 «실제로 받을 조합»에서 가져옵니다.** 같은 영상에서 240p 는 H.264+AAC 로 받아져 725 KB 라고 적혔고, 실제 파일은 727 KB(744,413바이트)였습니다. 파일 이름에는 영상 번호를 붙여서, 같은 제목끼리 덮어쓰지 않게 했습니다.

## 남는 원리 하나
**보여 주는 규칙과 고르는 규칙은 한 곳에서 나와야 합니다.** 고르는 일은 한 군데서 하고 보여 주는 일은 다른 점수식으로 따로 하면, 화면은 조용히 거짓말을 합니다. 에러도 안 납니다. 이번에 만든 스크립트는 목록을 만들 때도 실제 받을 때 쓰는 선택 규칙을 그대로 yt-dlp 에 물어봅니다.

## 못 한 것
- **yoinks 를 설치해서 돌려 보지 않았습니다.** 화면 도구라 읽고, 선택 함수만 떼어 실행했습니다. 화면 동작은 모릅니다.
- **영상은 하나, 사이트는 유튜브 하나입니다.** 크기 정보가 비는 일이 얼마나 흔한지는 못 쟀습니다. 이 영상에서는 240p 후보 일곱 개 중 둘이 비어 있었습니다.
- **받은 파일을 퀵타임이나 편집기에서 열어 보지 않았습니다.** 코덱이 다르다는 것까지만 확인했습니다.
- **/watch 가 받은 파일을 남겨 두는지는 열어 보지 않았습니다.** 남겨 둔다면 제 스크립트는 거의 겹칩니다. 지금은 「분석용 임시 폴더」와 「오래 보관하는 레퍼런스」를 가르는 쪽으로 두었습니다.

## 여기부터는 자세한 기록입니다
**yoinks 는 yt-dlp 위에 Ink(터미널용 React) 화면을 얹은 단일 작성자 프로젝트이고, 판정은 도구 도입 기각 · 기법 수확 3종 채택이다.** 핵심 발견은 구현에서 나왔다. README 는 해상도별 크기를 보여 준다고 하지만, 그 크기를 계산하는 후보(점수 1등)와 실제 `-f` 선택자가 서로 다른 규칙이라 **화면의 크기·코덱이 실제 파일을 보장하지 않는다.**

## 무엇을 하는 물건인가
MIT 라이선스, TypeScript 약 1,900줄. 흐름은 네 단계다.
| 단계 | 하는 일 | 구현 |
|---|---|---|
| 1. 도구 확보 | 시스템 `yt-dlp` → `~/.yoinks/bin` → 없으면 GitHub 릴리스에서 내려받음 | `ensureYtDlp` |
| 2. 읽기 | `yt-dlp -J --no-playlist` 로 영상 정보를 한 번 읽어 임시 파일에 저장 | `probe` |
| 3. 선택지 | 높이별로 줄을 만들고(최대 8개) 소리 전용 mp3 줄을 붙임 | `buildChoices` |
| 4. 받기 | `--load-info-json` 으로 재추출 없이 받고, 진행률은 `--progress-template` 으로 파싱 | `download` |

ffmpeg 는 PATH 에 있으면 yt-dlp 가 알아서 쓰고, 없으면 `ffmpeg-static` 을 폴백으로 쓴다. 저장 위치는 `~/Downloads` 고정이다.

## 대표 설계 결정 — 성립 조건까지 같이 적는다
| 결정 | 구현 | 성립 조건 |
|---|---|---|
| **정보 1회 읽기 + 재사용** | 읽은 JSON 을 임시 파일로 두고 받을 때 `--load-info-json` | 읽기와 받기 사이에 주소가 만료되지 않을 것. 서명 URL 이 짧게 만료되는 사이트에서는 받기가 실패할 수 있다 |
| **높이 폴백 선택자** | `bv*[height=N]+ba/b[height=N]/bv*[height<=N]+ba/b` — 정확히 N, 없으면 N 이하 | 그 높이 영상이 있다는 전제. 선택자가 «어느 코덱»은 정하지 않는다 |
| **취소 시 정리** | 받는 동안 yt-dlp 가 찍는 대상 경로를 모아 두었다가 취소되면 `.part`·`.ytdl` 까지 삭제 | 출력 줄 형식(`[download] Destination:`)이 안 바뀔 것 — 문자열 파싱에 의존한다 |
| **진행률 파서** | 출력 템플릿으로 `YOINK|…` 줄을 찍게 해서 숫자 파싱 | 바이트가 줄어들면 «다음 조각»으로 센다. 합쳐 받기(영상+소리)에서만 맞는 추정이다 |

## 깨본 결과 — 확정된 것 넷

### ① 크기 표시가 실제 선택과 따로 계산된다
`buildChoices` 는 높이별로 후보를 고른 뒤 점수(`tbr` + mp4 확장자 1만 점 + `avc` 5천 점)가 제일 높은 하나를 `best` 로 잡고, **그 `best` 의 크기로 줄을 적는다.** 그런데 줄의 `args` 에는 `best` 의 포맷 번호가 들어가지 않는다. 높이만 들어간다. 즉 `best` 는 **라벨 전용**이다.

2026-11-12 실측(yt-dlp 2026.08.19, 영상 `jNQXAC9IVRw`, `buildChoices` 원문을 그대로 실행):
| 줄 | 적힌 크기 | 실제로 고르는 조합 |
|---|---|---|
| 240p | ~302 KB | `395+251` (AV1 + Opus) = 475,961 바이트 |
| 144p | ~302 KB | `278+251` (VP9 + Opus) |
| 소리만 | ~302 KB | — |

240p 의 점수 1등은 `230`(H.264)인데 크기 필드가 비어 있어 `0 + 소리 크기(309,288)` = 302 KB 가 됐다. 실제 받는 것은 yt-dlp 의 기본 정렬이 고른 AV1 이다.

### ② 열린 이슈 속에 같은 증상이 있다
이슈 제목만 읽었다. 「퀵타임에서 안 열리는 HD 영상」(#40), 「퀵타임 호환 H.264/AAC 옵션 요청」(#32), 같은 요구의 PR(#33). 코덱을 정하지 않는 선택자와 이어지는 모양이지만, 재현은 하지 않았다.

### ③ 받는 프로그램을 검증 없이 내려받는다
시스템에 yt-dlp 가 없으면 `releases/latest/download` 에서 실행 파일을 받아 `chmod 755` 하고 쓴다. 체크섬·서명 확인이 없다. 그리고 한 번 받은 뒤에는 **갱신하지 않는다**(자체 갱신은 README 로드맵에 미완료). 사이트가 바뀌어 yt-dlp 가 낡으면 이 도구는 조용히 안 받아지는 상태가 된다.

### ④ README 가 코드보다 낡았다
로드맵에는 「클립보드 주소 감지」가 미완료로 남아 있는데, `src/lib/clipboard.ts` 와 `cli.tsx` 에 구현이 이미 있다. 거꾸로 말하면 이 저장소의 문서는 구현을 따라가지 않는다.

## 적용처와 시험
옮긴 곳은 `~/.claude/game-team/scripts/ref_video.py`(문스튜디오 레퍼런스 영상 받기)다. 같은 영상으로 시험한 결과는 이렇다.
| 시험 | 결과 |
|---|---|
| `--list` | 240p → H.264 · 725.0 KB, 144p → H.264 · 492.7 KB |
| 기본 받기 | 240p mp4 744,413 바이트, ffprobe: H.264 + AAC |
| 같은 명령 재실행 | 「이미 있음」 — 덮어쓰지 않음 |
| `--audio` | mp3 331,053 바이트 |
| 없는 영상 주소 | 오류 한 줄 · 종료 코드 1 · 출력 폴더에 임시 폴더 안 남음 |

H.264 를 우선하면 같은 해상도에서 **파일이 더 크다**(AV1 476 KB vs H.264 725 KB). 용량보다 호환을 택한 것이고, 값은 위 표에 같이 보인다.
