**기획서를 넣으면 «테스트 케이스»가 표에 채워집니다. 핵심은 「AI가 써 준다」가 아닙니다 — 그건 아무나 엉망으로 할 수 있습니다. 진짜는 «AI에게 무엇을 안 맡겼는가»입니다.**

## 먼저 — 「테스트 케이스」가 뭔가요

게임이나 앱을 만들면 **제대로 되는지 확인**해야 합니다. 그런데 「잘 되나 봐 주세요」로는 확인이 안 됩니다. **뭘 눌러서 뭐가 나와야 하는지**를 미리 적어 둬야 합니다.

그 적어 둔 한 줄이 **테스트 케이스**입니다. 대략 이런 모양입니다.

| 항목 | 내용 |
|---|---|
| **무엇을** | 아이템 강화 |
| **어떻게** | 강화석 없이 강화 버튼을 누른다 |
| **그러면** | 「재료가 부족합니다」가 뜨고 강화가 안 된다 |

이런 걸 기능 하나에 수십 개씩 씁니다. **손으로 쓰면 오래 걸리고, 쓰다 보면 빠뜨립니다.**

이 도구는 **기획서를 넣으면 이 표를 채워 줍니다.**

## 핵심은 「AI가 쓴다」가 아닙니다

여기가 이 도구의 정체입니다.

**AI에게 「테스트 케이스 써 줘」 하면 씁니다.** 그건 누구나 할 수 있습니다. 문제는 **결과가 매번 다르다**는 것입니다.

- 오늘은 번호가 1부터고 내일은 0부터
- 어떤 날은 열이 여섯이고 어떤 날은 일곱
- 같은 기획서를 두 번 넣으면 **결과가 다름**

그래서 이 도구는 **역할을 갈랐습니다.**

| 누가 | 무엇을 소유하나 |
|---|---|
| **코드**(정해진 프로그램) | **순서 · 표의 뼈대 · 번호 · 서식 · 빠짐없이 챙겼는지 원장 · 표에 쓰기** |
| **AI** | **문장 · 설계 판단 · 지적 · 판정** |

즉 **AI는 「말」만 쓰고, 「모양」은 전부 코드가 잡습니다.**

왜 이렇게 했냐면 — **처음엔 AI가 전부 몰았는데, 하다 보면 자기가 정한 규칙에서 슬슬 벗어났습니다.** 30번째 줄쯤 가면 서식이 달라져 있습니다. 나쁜 뜻이 있어서가 아니라 **원래 그런 성질**입니다.

**모양을 코드가 쥐고 있으면 벗어날 수가 없습니다.**

## 여덟 단계로 돕니다

| 단계 | 하는 일 | 주인 |
|---|---|---|
| **0** | 원문 모으기, 다른 사람이 동시에 못 돌리게 잠그기, **입력이 멀쩡한지 자가 점검** | 코드 |
| **1** | 기획서 읽고 **설계 뼈대** 만들기 | AI |
| **2** | 설계가 쓸 만한지 **검문** | 코드 |
| **3** | 뼈대 만들고 → **문장 쓰기를 여럿이 나눠서** → 합치기 | 코드 + AI |
| **4** | **적대적으로 검토** · 판정 · 빠짐없이 챙겼는지 기록 | AI |
| **5** | 수정 적용 + **검문 4종** | 코드 |
| **6** | **실제 표에 쓰기** | 코드 |
| **7** | 마무리 · 대시보드 · 알림 | 코드 |

## 성격을 정하는 것 — 「못 넘으면 섭니다」

이 도구는 **「최선을 다해 계속」하지 않습니다.**

중간중간 검문소가 있고, **못 넘으면 멈추거나 되돌아갑니다.**

| 검문소 | 걸리면 |
|---|---|
| 입력 점검 | 한 번 다시 모아 보고, 또 실패하면 **아예 시작 안 함** |
| 설계 검문 | **1단계로 되돌려** 고침 |
| 합치기 대조 | **어긋난 조각만** 다시 |
| 수정 적용 | **「거부」가 정상 동작** — 고칠 대상이 예상과 다르면 안 고침 |
| 표현 검문 | **두루뭉술한 말**을 막음 |
| 중복 검문 | 똑같은 케이스가 남아 있으면 합치게 함 |
| 누락 검문 | **안 챙긴 규칙이 있으면** 행을 보태고 다시 |

네 번째 줄이 특히 중요합니다. **「고치려고 열었는데 내용이 예상과 다르면 안 고치고 멈춥니다.」** 사이에 누가 손댔을 수 있으니까요. **거부가 고장이 아니라 정상 동작**입니다.

## 검토는 협력이 아니라 「적대」입니다

만들어진 케이스를 **여러 시선이 «동시에» 읽습니다** — 구조 보는 눈, 품질 보는 눈, 원문과 대조하는 눈.

그리고 **서로의 결과를 모릅니다.**

일부러 그렇게 했습니다. **서로 알면 의견이 수렴하고, 수렴하면 «같은 것»을 같이 놓칩니다.** 셋이 따로 봐야 셋이 다른 걸 잡습니다.

## 값을 치르고 배운 것 — 「번호로 이으면 안 됩니다」

제일 아팠던 자리입니다.

빠짐없이 챙겼는지 기록하는 장부가 있는데, 처음엔 **케이스 번호로** 가리켰습니다 — 「3번 규칙은 7번 케이스가 담당」처럼요.

그런데 **중간에 행을 하나 끼워 넣으면 그 뒤 번호가 전부 밀립니다.** 7번이 8번이 됩니다. 장부는 여전히 7번을 가리키는데, **7번은 이제 다른 케이스**입니다.

처음엔 **계산해서 다시 매기려** 했습니다. **틀렸습니다.** 끼워 넣기가 여러 번 일어나면 계산이 안 맞습니다.

지금은 **번호가 아니라 «내용»으로 잇습니다** — 분류 + 확인 단계 + 재현 방법을 조합해서요.

> **위치는 변하고 내용은 안 변합니다.**

## 정직한 한계

**기획서가 부실하면 결과도 부실합니다.**

이 도구는 **없는 기획을 지어내지 않습니다.** 근거가 없으면 케이스를 만드는 대신 **「기획 확인 필요」로 표시하고 넘어갑니다.**

저는 그게 맞다고 봅니다 — **지어낸 케이스는 나중에 「이거 어디서 나온 거야」가 되고, 그때는 아무도 답을 모릅니다.**

다만 **기획이 얇은 조직에서는 산출량이 기대보다 적게 나옵니다.** 그건 도구 탓이 아니라 **재료 탓인데, 쓰는 사람에게는 똑같이 실망**입니다.

## 기각한 것들

버전 기록은 대체로 **「진척처럼 보였는데 아니었던 것」의 목록**입니다. 만든 것보다 **뺀 것**이 더 많습니다.

> **[도판]** 검은 칸은 결정론 코드가, 주황 칸은 모델이 맡는다. S3만 두 레인을 오간다 — 코드가 골격을 만들고, 모델이 문장을 채우고, 코드가 다시 병합한다. 삼각형은 게이트고, 못 넘으면 그 자리에서 선다.
>
> S0부터 S7까지 여덟 단계를 코드 레인과 LLM 레인으로 나눈 흐름도. 코드가 S0·S2·S5·S6·S7을, LLM이 S1·S4를 맡고 S3은 두 레인을 오간다. 게이트는 S0·S2·S3·S5에 있다.

## 여기부터는 자세한 기록입니다

기획서 원문을 넣으면 라이브 스프레드시트 탭에 테스트케이스 세트가 채워진다. 시작부터 끝까지 한 번의 호출로 돈다.

핵심은 "LLM이 TC를 쓴다"가 아니다. 그건 아무나 엉망으로 할 수 있다. 진짜는 **역할을 가른 것**이다.

> **2레인 원칙 — LLM은 문장과 판단만, 결정론 코드가 구조와 사실을 가진다.**

## 왜 갈랐나

초기엔 모델이 파이프라인 전체를 몰았다. 드리프트했다.

단계마다 행 수가 달라지고, 커버리지가 조용히 떨어지고, **두 번 돌려서 같은 모양이 나온 적이 없었다.** 모델은 "대충 맞게" 하는 데는 훌륭한데, 같은 입력에 같은 출력을 내는 데는 쓸 수 없다.

해법은 설득이 아니라 **몰수**였다.

| 소유자 | 가진 것 |
|---|---|
| 결정론 코드 | 단계 순서, 행 골격, 번호, 서식, 병합, 커버리지 원장, 시트 기록 |
| LLM | 설계 판단, 문장, 리뷰 지적, 판정 |

## 여덟 단계

| 단계 | 하는 일 | 주인 |
|---|---|---|
| **S0** | 원문 수집, 실행락, 입력 자가검증 | 코드 |
| [**S1**](/ko/built/tc-team/s1/index.md) | 기획서 분석 → 설계 골격 | LLM |
| [**S2**](/ko/built/tc-team/s2/index.md) | 설계 격리 게이트 + 원문 슬라이스 | 코드 |
| [**S3**](/ko/built/tc-team/s3/index.md) | 골격 생성 → 문장화 팬아웃 → 병합 | 코드 + LLM |
| [**S4**](/ko/built/tc-team/s4/index.md) | 적대 리뷰 · 판정 · 커버리지 원장 | LLM |
| [**S5**](/ko/built/tc-team/s5/index.md) | 수정 적용 + 게이트 4종 | 코드 |
| [**S6**](/ko/built/tc-team/s6/index.md) | 라이브 시트 기록 | 코드 |
| [**S7**](/ko/built/tc-team/s7/index.md) | 완료 처리 · 대시보드 · 알림 | 코드 |

S1~S7은 각각 따로 적어 뒀다. 단계마다 값을 치르고 배운 게 하나씩 있어서, 표 한 줄로는 안 담긴다.

S3이 이 구조를 가장 잘 보여준다. **골격을 코드가 먼저 만들고**, 25행씩 잘라 모델에게 문장만 채우게 하고, 돌아온 것을 코드가 다시 병합한다. 병합할 때 인덱스·에코·해시·개수를 대조해서, 모델이 행을 밀거나 남의 행을 건드렸으면 **그 청크만 다시 돌린다.** 나머지 청크의 결과는 그대로 살린다.

## 게이트 — 못 넘으면 선다

이게 이 도구의 성격을 정한다. **"최선을 다해 계속"하지 않는다.**

| 게이트 | 단계 | 걸리면 |
|---|---|---|
| 입력 자가검증 | S0 | 재수집 1회 → 또 실패면 **시작 금지** |
| design_gate | S2 | 설계 결함 → S1으로 되돌려 수정 루프 |
| merge 대조 | S3 | 어긋난 청크만 재실행 |
| apply before-불일치 | S5 | **거부가 정상 동작** — 수정 계획 재생성 |
| content_gate | S5 | 추상 표현·근거 없는 위임 차단 |
| dup_gate | S5 | 완전 동일 케이스 잔존 시 병합 강제 |
| traceability | S5 | 규칙 미커버 → 행 봉합 후 재적용 |

`apply before-불일치`가 특히 중요하다. 수정을 적용하기 전에 **"내가 고치려는 그 자리가 아직 내가 본 그 내용인가"** 를 확인하고, 다르면 거부한다. 사람이 중간에 시트를 만졌거나 앞 단계가 밀렸다는 뜻이라, 이때 밀어붙이면 엉뚱한 행을 덮어쓴다.

멈추는 지점은 딱 하나로 모아뒀다. 무결성 위반이면 즉시 서고, 그 외에는 무인으로 완주한다.

## 리뷰는 협력이 아니라 적대다

생성된 케이스를 **렌즈 여럿이 병렬로** 읽는다 — 구조, 품질, 원문 대조. 서로의 결과를 모른다. 알면 수렴하고, 수렴하면 같은 걸 놓친다.

별도의 판정자가 이 지적들을 교차신문해 오탐을 떨어내고, **기계가 적용 가능한 형태의 수정 계획**을 만든다. 살아남은 지적은 코드가 적용한다. 모델에게 "고쳐주세요"라고 부탁하지 않는다.

같은 단계에서 커버리지 원장을 만든다. 기획서에서 뽑아낸 규칙 하나하나가 어느 케이스로 덮였는지를 기록하고, 안 덮인 규칙이 있으면 S5에서 행을 봉합한다.

## 시트는 한 번만 만진다

S6은 라이브 시트를 **딱 한 번** 접촉한다. 그리고 소유 마커로 판단한다.

- 우리가 만든 탭이면 → 통째로 지우고 다시 쓴다 (멱등)
- 남이 쓰던 탭이면 → 침범하지 않고 `_v2` 접미사로 새로 만든다
- 다른 탭은 무조건 불가침

여러 번 돌려도 결과가 같고, 남의 작업을 절대 덮지 않는다. 자동화가 사람 옆에서 돌려면 이 두 개가 먼저다.

## 값을 치르고 배운 것 두 개

**행을 끼워 넣으면 번호가 밀린다.** 커버리지 원장은 케이스 번호로 규칙을 가리키는데, 봉합으로 행을 추가하면 그 번호가 통째로 낡는다. 처음엔 산술로 다시 매기려 했다 — 틀렸다. 지금은 **번호가 아니라 내용으로 잇는다**(분류 + 검증 단계 + 재현 스텝). 위치는 변하고 내용은 안 변한다.

**손으로 몰면 절반이 사람 대기 시간이다.** 한 번은 단계를 하나씩 손으로 돌렸는데, 벽시계로 2시간 23분 걸린 런에서 **기계가 실제로 일한 시간은 1시간 12분**이었다. 나머지는 전부 내가 다음 명령을 치는 걸 기다린 시간이다. 무인 완주를 만든 이유가 이 숫자다.

## 기각된 것들

버전 히스토리는 대체로 **"진척처럼 보였지만 아니었던 것"** 의 목록이다.

어휘 기반 진척도 감지 — 실측 2회로 기각. 임계값 통일 — 기각. 확신도 히트맵은 모델 채점판이 재현에 실패한 뒤, **모델 호출 0회의 순수 결정론 산출**로 끝났다.

기각할 때마다 재개 조건을 같이 적었다. 안 그러면 반년 뒤에 같은 아이디어를 다시 꺼내게 된다.

## 정직한 한계

기획서가 부실하면 결과도 부실하다. 이 도구는 **없는 기획을 지어내지 않는다** — 근거가 없으면 케이스를 만드는 대신 "기획 확인 필요"로 표시하고 넘어간다. 그게 맞다고 보지만, 기획이 얇은 조직에서는 산출량이 기대보다 적게 나온다.
